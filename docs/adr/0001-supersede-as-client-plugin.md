# 会话级"接替"开关做成纯客户端插件，不改核心包

在"运行中发消息"这条路上，DSH 只有排队（`queue`）和插话（`steer`）两种语义，用户想要第三种：立刻中止当前轮次、以新消息重开。真正决定形态的事实是：模式判定坐在 `@deepseek-ai/dsh-client-ui-conversation` 内部（`BUSY_ENTER_BEHAVIORS` 是闭集），而这个包随应用出厂（`list_bundles` 里 `availability: installation`），不落在 profile 的 `node_modules` 里，插件市场装的包碰不到它。因此决定：做成**纯客户端插件**——会话级开关 + 观察队列新行 + `ctx.remote.session.cancel({sessionId})`——不去 fork 那个包。

## 考虑过的选项

- **fork `dsh-client-ui-conversation`，把第三个值加进 `BUSY_ENTER_BEHAVIORS`**：语义最干净，发送按钮的文案也能改对。但要靠 bundle 的 `overrides` 覆盖核心行，并长期追上游版本 rebase。放弃原因是维护成本，不是技术不可行。
- **客户端 + 宿主半边**（宿主监听 `agent/inbox/inserted`，进程内取消）：零竞态。但开关状态只能用会话命令（`ctx.remote.commands.execute`）传给宿主，会在斜杠菜单里多出一条命令；第三方包能否自建 Remote 端点也未经证实。
- **拦截提交流**：客户端没有提交扩展点——插件拿到的 `InputActions.submit()` 不带模式参数，而客户端事件只有 `connection/reset`、`locale/change`、`slots/changed`、`theme/change`。做不到。

## 后果

- 发送按钮仍显示"排队"，与实际行为不符；靠开关旁的"接替中"标签兜底。
- `cancel` 是一次远程往返，存在窄窗口可能误杀刚刚开跑的新轮；后果是"用户消息 + 一个空轮次"，重发即可。
- 接替留痕只存在浏览器内存，刷新页面后被打断的轮次会退回成普通中止。
- 队列行的"接替发送"做不了：队列行由会话 UI 自己渲染，行内没有插件槽。

## 后续修正：取消不会自动续跑队列（2026-11-26）

实现完成后的现场反馈推翻了本 ADR 与规格共同依赖的一条运行时判断："宿主取消保留收件箱，并在 `turn/end` 后由待处理队列自动开下一轮"在装机版本（0.2.2-rc.5）不成立：被中止的驱动在 `agent-loop` 的 `turn()` 中直接抛出，队列行会留在 `next-turn` 直到下一次 prompt。

纯客户端插件没有"唤醒收件箱"的公开能力，因此实现改成：取消被接受后，把触发这次接替的纯文本队列行 `updateQueue(remove)` 取出，再用新 requestId `prompt(..., 'queue')` 重新投递——这条 prompt 在已中止的 phase 上会 latch 一次唤醒，aborted 驱动收尾后由它开出下一轮。代价是消息换了一个身份，且带附件/图片的消息无法重投（留在队列、当前轮继续，不接替）。这不改变"纯客户端、不改核心包"的决定，只是补上了缺失的唤醒这一步。

## 后续修正：空闲发送不会被自己开启的轮次打断（2026-11-26）

现场反馈：会话空闲时开着开关发消息，这条消息开启的那一轮会立刻被插件取消，再被重新投递成第二轮——用户看到的是"刚发的消息被停止了"。根因是判定只看观察时的 `running`：空闲提交后宿主先插入队列行、再启动轮次，客户端可能在同一批观察里同时看到"新队列行 + running"，于是把这条消息误当成运行中提交。

修正保留"只认持久化队列行"的触发点，但要求这条行**不是它自己开启的那一轮**：插件按 `PendingSubmission.placement`（提交时客户端是否 running，`transcript` 即空闲）记住本机空闲提交的 request id；并只在"上一次观察已经看到同一个 open turn"时才把新行当候选。任一条件不满足的行只记录、不动作，且照常进入 `seen`，之后不会补触发。判定的纯函数因此新增 `ineligible` 入参。代价是"行与 open turn 同批首次到达"的极快连续发送会退回原生排队而不是接替——按"证据不足就排队"处理，与插件的 fail-closed 原则一致。
